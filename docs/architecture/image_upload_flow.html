RS Fashions — Image Processing Pipeline

HEIC Conversion · Sharp Optimization · Supabase Storage

1. Frontend Selection

1
Admin selects product image in SareeStock.tsx. If it's an iPhone photo (HEIC/HEIF format), the browser attempts client-side conversion using heic2any. If that fails, it calls the backend conversion endpoint.
POST /api/upload/convert-heic
2
Admin submits product form. Images are sent as base64 data URLs inside the product JSON payload.
POST /api/admin/catalog/products Body: { name, price, ..., images: ["data:image/jpeg;base64,..."] }
↓

2. Backend Processing (upload.controller.js)

3
Buffer Extraction: Backend extracts the raw binary Buffer from the data URL.
4
Server-Side HEIC Check: Checks magic bytes to see if it's still a HEIC file. If so, runs heic-convert. CPU INTENSIVE
await heicConvert({ buffer, format: 'JPEG', quality: 0.9 })
5
Sharp Optimization: The Sharp library optimizes the image.
sharp(buffer) .rotate() // Extremely important: fixes EXIF orientation from phone cameras .resize({ width: 1200, height: 1200, fit: 'inside' }) .jpeg({ quality: 82, progressive: true, mozjpeg: true }) .toBuffer()
↓

3. Supabase Storage Upload

6
Upload to Bucket: The optimized buffer is uploaded to Supabase Storage.
supabase.storage.from('sarees').upload(`uploads/${fileName}`, optimizedBuffer, { contentType: 'image/jpeg', upsert: false })
7
Get Public URL: Generates the CDN URL for the image.
supabase.storage.from('sarees').getPublicUrl(`uploads/${fileName}`)
8
Fallback Mechanism: If Supabase Storage is unreachable or fails, the system falls back to returning the optimized base64 data URL.

⚠️ Note: Storing data URLs directly in the products table database row bloats the database size significantly, but ensures the system works entirely offline.
